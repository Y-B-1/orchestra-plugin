# Hook policy and boundaries

One classifier and two native adapters replace duplicated provider guards. Commands use a supported Python runtime and quoted plugin paths. Hook files are separate to prevent default discovery from loading duplicate handlers.

| Event | Effect | Does not do |
| --- | --- | --- |
| SessionStart | Supply main or worker contract and skill path; add the session id for `start --harness-session`; show a pending autonomy morning report | Seed state, repair files, resume, arm autonomy |
| SubagentStart | Supply worker boundaries to agents whose type starts with `orchestra:`; during an active run, tell any other agent to stop (advisory); otherwise return nothing | Veto native startup or authenticate identity |
| PreToolUse | Classify the call and deny covered destructive Git, stash, wholesale staging, protected state/config patches; check recognizable releases and, under autonomy, approval boundaries. Timeout 30 seconds, because the merged checks run Git | Interpret arbitrary scripts, aliases, stdin or all provider tools |
| Stop | Continue only when the coordinator can act now: a ready or reported card, an open final finding, a held chain owed its final review, or, with every card accepted, the final review, gates and pull request still owed. Running workers alone let the turn end (the harness wakes the session when one finishes), and a continuation is never repeated for an unchanged progress signature. Autonomy stops at the deadline, completion, a tampered ledger, a stall with no worker running, only parked cards, no live card or disarm; no pass or stall count stops it | Start an unrequested loop or continue corrupt state |
| SessionEnd | Release the run bound to the ending session (see below) | Release on `clear` or `resume`; release a run started without `--harness-session` |

The PreToolUse matcher is `Bash|Edit|Write|MultiEdit|Agent|Task`; an Agent or Task call carrying `agent_id` (made inside a subagent) is denied with "Workers do not delegate", and a fresh mod marker never skips the Python hook for those two tools.

## Session end and the lease

`start --harness-session ID` binds the run to the Claude Code session. When that session ends with reason `logout`, `prompt_input_exit`, `other` or an unknown reason, the SessionEnd hook interrupts the run, so a lost lease never locks the next session out. On `clear` and `resume` the process continues under a new id and the run stays armed: the hook records a pending rebind, and the next SessionStart with source `clear`, `resume` or `fork` within 60 seconds binds the run to the new id. Runs started without a harness session are untouched. If the binding is lost anyway, read the actor and lease from `state.json` in the state directory and run `interrupt` with them; the lease is a consistency token, not a secret.

Claude's package has no Interrupt event. On user interruption, the main must stop workers through the harness and run the CLI `interrupt` before further dispatch. Late results cannot advance an interrupted engine run. An OS crash or hook timeout cannot prove that interruption was recorded: inspect actual processes and state before resuming.

## Command classes

The guard sorts every shell command into one class. Classification does not depend on run state; the hook then applies the run state.

| Class | Meaning | No run | Run active | Autonomy active |
| --- | --- | --- | --- | --- |
| `allow` | No rule applies | allow | allow | allow |
| `deny` | Always-deny rule, malformed command or protected path | deny | deny | deny |
| `release` | One release-class command alone (non-force `git push`, `gh pr merge`, a `gh api graphql` mutation or body from `--input` or a `=@file` field, a `gh api` call that mentions merge such as `gh api -X PUT repos/o/r/pulls/1/merge` or a `mergePullRequest` mutation, `gh release create`, package publish including `cargo publish`, provider deploy) | allow | allow with a current permit, else ask the user | deny, except the pull request push and the pre-authorized release |
| `release-multi` | A release-class command inside a multi-command line | allow | ask the user | deny |
| `boundary` | Deletion (`rm`, `git branch -d`, `git worktree remove` and similar) or local merge, pull, rebase, cherry-pick | allow | allow | deny, except merged cleanup (below); a local merge is allowed on a non-default branch |

Always denied whatever the state: force or mirror push, `+refspec`, `--all`, `--tags`, several destinations, `reset --hard`, `clean -f` without `-n`, wholesale `add`, `commit -a`, wholesale checkout or restore, `switch -f`, and every `git stash` form, `list` and `show` included. A `--delete` push or `branch -D` is denied too unless it meets the merged-delete rules below. Raw ref deletion through `git update-ref` (`-d`, `--delete`, `--stdin`, or an all-zero new value) is always denied with "Raw ref deletion is not allowed; use git branch -d". `git restore --staged` is allowed. Outside a run, release-class commands are allowed so ordinary pushes and pull request merges work. Inside a run, a current engine permit lets a release run; otherwise Claude Code asks the user. Under autonomy, releases are denied except the pull request push and the pre-authorized release. A state file that exists but cannot be loaded (policy or repository changed, malformed) counts as an active run with no permit, and as autonomy-active when its raw flag says so or it is not valid JSON. The one exception is a state that parses with `session` null or `session.active` false: that ended run is inactive.

Shell parsing removes heredoc bodies and redirections first. A heredoc or here-string body is classified as a script when its consumer is a shell, `source`, `.`, `eval` or `xargs` running a shell, and is scanned for always-deny lines whatever the consumer. Command runners (`xargs`, `find -exec`, `doas`, `stdbuf`, `watch`, `flock`, `sudo`, `env` and similar) are unwrapped so the real command gets its class. Accepted costs: a data heredoc or producer that contains a bare destructive line denies, and a runner that ends in `-c` with no payload denies as malformed.

Accepted limits, because the guard is best effort and not hostile-worker isolation: encoded payloads (base64, `printf` escapes other than `\n`), variable or alias indirection, non-shell interpreters (`python3 -c`, `perl -e`, `node -e`), output process substitution, zsh `=(...)`, and `script` as a runner. Bash writes to protected paths, including the autonomy ledger and the mods marker directory, are not detected. Credential entry is not detected. `gh api` calls that do not mention merge, and MCP or terminal tools that push or merge, are not guarded; using them to get around the guard is forbidden by procedure, not enforced. The guard refuses to set a Git alias or a push mapping (`git -c alias.*=…`, `git config alias.*`, `remote.<name>.push`, `remote.<name>.pushurl`), but it does not resolve an alias that already exists, so one defined earlier can still run a push or merge under another name. The run is found from the session directory, so a `git -C <run repo> push` issued from outside that repository is not seen as part of the run.

A linked worktree of a repository with a run gets the same state: the hook resolves the run from the main worktree. A separate clone is a different repository and has no run. Protected paths are the hook and config files of each harness, Orchestra agent files, any `.orchestra` component, the run state directory (except the coordinator's `progress.md`, `standing-orders.md` and `autonomy.md`) and the mods marker directory. `settings.json` is not protected.

## Agent guard and reviewer test block

- **Agent guard.** While a run is active (the hook loaded an engine whose session is active), an `Agent` or `Task` call from the main session whose `subagent_type` does not start with `orchestra:` is denied with "Orchestra run active: use an orchestra:* agent (investigator-code for search, builder for edits)". A missing, empty or non-string `subagent_type` counts as non-Orchestra. Outside a run nothing changes, and a call made inside a subagent still hits "Workers do not delegate". If the loaded engine errors while the hook checks the session, the call is denied only when the raw state file shows an active (or unreadable) session; an inactive raw session allows it.
- **Subagent guard.** While a run is active, any tool call made inside a subagent whose `agent_type` does not start with `orchestra:` is denied with "Orchestra run active: this agent is not an orchestra:* agent; stop and report. Start Agent and Workflow workers with an orchestra:<role> type". This covers agents a Workflow script starts, which never pass through `Agent` or `Task`; a Workflow agent with no `agentType` arrives as `workflow-subagent`. Such calls skip the mod fast path, so the Python guard always decides them. `SubagentStart` cannot block an agent, so during a run it gives a non-Orchestra agent the same text as context. The PreToolUse matcher covers shell, edit and agent tools only, so a read-only non-Orchestra agent can still read files; it is told to stop but not forced. `agent_type` is a routing hint, not authentication.
- **Reviewer test block.** A shell call from a subagent whose `agent_type` starts with `orchestra:code-reviewer` or `orchestra:critic` that runs a test suite is denied while `engine.current_gate_ids()` returns ids: "Cite gate receipt <ids>; reviewers do not rerun suites". Suite commands are `pytest`, `python -m pytest`, `python -m unittest`, `npm test` and `npm run test*` (also `pnpm`, `yarn`), `npx vitest`, `npx jest`, `npx playwright test`, `go test`, `cargo test` and `make test`, alone, after `cd x &&`, behind `env`, `time`, `uv run` or `bash -c`. A single-test probe is allowed: one unittest target naming a method (`tests.test_x.Class.test_y`) or one pytest `file::test` target. With no engine, an engine without `current_gate_ids`, an error from it or an empty list, the call is allowed. A fresh mod marker never lets these calls skip the Python hook, because only Python holds this rule. Like every shell rule it is best effort: an interpreter one-liner or encoded payload that runs a suite is outside it.

## Merged-branch deletion

`git branch -D <b>`, `git branch --delete --force <b>` (also `-d -f`, `-df` and abbreviated options) and `git push <remote> --delete <b>` or `-d <b>` (any prefix of `--delete`, flag before or after the remote) form the `merged-delete` category. It is a delete boundary, not a new boundary kind. Each needs exactly one branch and no other option, and the remote must be a name, not a URL or path. Multi-branch deletes, `:branch` refspecs, a forced remote-tracking delete and `--delete` with other push options stay denied.

A merged-delete must stand alone. A command line of more than one segment containing one is denied ("Execute branch deletions separately"), and so is one with `-C`, `--git-dir`, `--work-tree`, a `GIT_DIR` or `GIT_WORK_TREE` assignment, a wrapper (`sudo`, `env`, `nice`, `xargs`) or a command substitution ("Branch deletion must run plainly in the session repository").

The Python hook then allows it only when the branch is merged, whatever the run state, and also when no engine can load. The branch must exist, must not be the default branch or the checked-out branch, and must be merged into the default branch by one of: the tip is an ancestor of it; the tip's tree appears among the default branch's first-parent commits (a squash merge); or the tip is an ancestor of a local or remote-tracking branch that meets the tree rule. Evidence is computed afresh at each delete. A remote delete also needs the remote's push URL to equal its fetch URL and `git ls-remote` (3 second timeout, no prompt) to return the tracking sha. Default refs are matched by exact full refname, and the deleted branch name must match its ref exactly, case included (on a case-insensitive filesystem the default and checked-out checks compare case-folded); a branch with a case-variant twin in the same namespace is never deleted. Otherwise the deny reads "Branch B is not merged into DEFAULT (no ancestor, tree or covering-branch evidence)". While autonomy is active a merged-delete is allowed on the same evidence, as cleanup (see Autonomy boundaries). `gate` refuses these commands and every other boundary command: they run only through the guarded hook.

## Hook failures and the session directory

- **Missing cwd.** A PreToolUse payload whose session directory no longer exists denies the delegated classes (release, release-multi, boundary) with "Session directory no longer exists: cd to an existing directory, then retry". Other classes behave as before. The mod spawns the Python hook from the plugin root and passes the session directory in the payload.
- **State busy.** Hook state reads wait up to 2 seconds for the state lock instead of blocking. When the lock is still held, PreToolUse denies the delegated classes with "Orchestra state is busy; retry"; every other class keeps the raw-state fallback. On Stop with autonomy armed in the raw state, the hook waits up to 8 seconds for the lock; if it stays held, the stop is allowed, one brief with reason `state busy` is appended to `progress.md`, and `state.json` is not changed, so the next Stop resumes the run. An unarmed Stop returns at once and writes nothing.
- **No Python 3.11.** `run-hook.sh` probes each candidate interpreter, so a broken shim (such as a pyenv shim with no installed version) is skipped. When none is Python 3.11 or later, PreToolUse fails closed (exit 2) and every other event only shows a warning (`systemMessage`, exit 0).
- **Guard errors name their class.** The mod's fail-closed reason reads "Orchestra guard error (spawn: CODE | exit N | timeout | bad output); failing closed"; an exit-2 deny shows its own reason.

## Autonomy boundaries

While `autonomy arm` is active, the hook and the engine enforce the approval boundaries: no release, permit or deploy; no push except the pull request push; no pull request merge; no deletion except merged cleanup; no local merge on the default branch. A denied boundary tells the coordinator to park the card with `park TASK --reason ...` and continue with other cards. Release permits stay unavailable until the user disarms, with one exception: when the ledger holds `- Release: pre-authorized <remote> <target>` equal to `policy.release`, a release-class command alone for that exact remote and target skips the autonomy deny and still needs a current permit, and the engine issues `permit` and `release` for that pair only. A release inside a multi-command line, every other push, merge, deletion and permit stay denied. Stop never arms autonomy by itself.

The pull request push is allowed only in the exact shape `git push <remote> <refspec>`, with `-u` or `--set-upstream` allowed anywhere in the command. The remote is a configured remote by name, not a URL, with neither `remote.<name>.push` nor `remote.<name>.pushurl` configured. No env prefix, wrapper, `-c`, `-C` or other push option is allowed. The refspec names one branch: `<branch>`, `HEAD` or `@` (the current branch), or `<src>:<branch>` or `<src>:refs/heads/<branch>`. The source must be a local branch, or `HEAD`/`@` on a branch. The destination must be a branch, never a tag or a `heads/`, `tags/`, `remotes/` or other `refs/` form, and it must differ, compared case-insensitively, from the remote's default branch, `main` and `master`. The default branch is the one the remote reported when autonomy was armed: `autonomy arm` runs `git remote set-head <remote> --auto` for every remote, stores each answer in the run state (`remote_defaults`) and reports it in its preconditions. A recorded `refs/remotes/<remote>/HEAD` alone is never trusted, since the remote may have changed its default; a remote that did not answer gets no pull request push until autonomy is armed again. The remotes are asked before the armed state is written, so an `arm` interrupted during that step leaves autonomy off. The destination is never the configured release target (that needs the pre-authorized permit), and a ledger armed with the 2.5 Push line `no push to any branch` allows no push. A bare `git push`, a detached `HEAD`, a force push or a push from another repository stays denied. `gh pr create` is not a release action. The owner merges the pull request after the run.

Merged cleanup: under autonomy the coordinator may clean up merged work. `git branch -d|-D <b>` and `git push <remote> --delete <b>` are allowed only when the branch is provably merged into the default branch (the merged-delete check above: ancestor, squash tree match or covering branch). `git worktree remove <path>` without `--force` is allowed only for a linked worktree of this repository whose checked-out branch passes the same check, and never for the session's own directory or the main worktree; Git itself refuses a dirty worktree. `git worktree prune` is allowed. Each must be a plain single command: no chaining, quoting, wrappers or `-C`. `rm` and every other deletion stay denied.

## Mods on Claude Code

The plugin registers a function-hook module (`hooks/mods.json`, loaded beside `hooks/claude.json`). It needs a Claude Code build that enables function hooks (`CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1`) and exposes the `$` APIs the module uses; tested on Claude Code 2.1.289 (CLI) and 2.1.286 (embedded in Desktop, with that variable set). There is no version floor. The module has no explicit API check. If a needed API is missing, session start fails, the guard stays not ready and guarded calls fall back to the Python hooks; if the module fails to load, the Python hooks guard every call. Both are the safe direction.

When active, the module classifies Bash, Edit, Write and MultiEdit calls in process with a TypeScript port of the same rules and writes a heartbeat marker under `${XDG_STATE_HOME:-$HOME/.local/state}/orchestra/mods/`. A fresh marker whose rules digest matches lets the Python PreToolUse hook return at once; a missing, stale or mismatched marker makes Python guard in full. Release, release-multi and boundary calls are always delegated to Python, because only the engine knows the run, permits and autonomy. A mod `tool.call` hook can deny but cannot ask, so for release and release-multi calls the Python PreToolUse hook never takes the fresh-marker shortcut: when the decision is to ask, the mod passes the call on and the native hook raises the prompt. The module also adds `/orchestra-board`, `/orchestra-autonomy on|off|status`, verdict and stop toasts and an autonomy status band, and appends the run's standing orders to briefs for `orchestra:` agents. These are display and convenience only. Without mods everything above still works through the Python hooks and the CLI.

## Release hooks

Release hooks check existing permits; a tool request cannot create one. Structured release execution independently checks configured authority, exact command, current final reviews and required gates. Known Git pushes need exactly four argv elements: the engine's resolved Git executable, push, the configured remote and one refspec. The source must resolve to the reviewed full HEAD. Wrappers and global/push options are rejected because they can change repository or destination context. Default policy names no remote, deployment, database operation or release command. Required missing scanners block; optional missing scanners report unavailable.

Workers retain documentation/browser tools and relevant state reads. Native profiles disable nested agent tools; prompts prohibit coordinator writes. Caller-supplied actor names and environment role markers are advisory consistency inputs. They do not authenticate a worker, and arbitrary interpreter writes are outside the shell classifier. Use host sandbox, remote branch protections and tool policies for stronger isolation.

Opening a session never installs old charter healers, stale-state rewrites, fixed product ports, relay forwarding, automatic rollback or source deployment recipes. ActionNotch and Orca integrations remain separate.

Claude Code does not automatically trust bundled hooks. Review and trust the current definition in the host interface; updates can need another review. Installer code never edits trust or uses a trust bypass.
