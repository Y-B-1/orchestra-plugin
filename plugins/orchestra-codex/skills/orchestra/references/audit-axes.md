# Conformance axes

Run one critic card per needed axis on the frozen candidate, before release. Each axis reports separately so every obligation stays visible. A report is semantic judgment, not machine proof. Judge the facts yourself; no command decides which axes apply.

| Axis | Run when | The critic checks |
| --- | --- | --- |
| spec | A substantial approved spec exists | Each requirement maps to an implementation seam and observable acceptance evidence. Quote missing and partial ones; separate unbuilt scope from a disputed requirement that needs design. |
| standards | Substantial binding standards apply | The cited rule against the concrete violation: scope, vocabulary, dependency direction, generated-source authority, accessibility. No invented project policy. |
| ledger | The run claims completion, approvals or gates | Claimed completion, approvals, gate artifacts, review independence and authorization against actual evidence: stale fingerprints, omitted failures, altered logs, unsupported release claims. |
| surface | By judgment: a shipped surface changed (command, API, UI, docs a user reads) | The shipped surface matches what the change promises and what users meet first. |

An explicit user-requested axis always runs. An unrelated card finishing triggers no audit. Code defects found go to builder repair; a rule or spec contradiction goes to design or planning. The code review and the gates may run beside the axis cards when all read the same unchanged artifact.
